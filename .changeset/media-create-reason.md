A shell-owned `media.session.create` that fails now says why. Until now every failure read `source unavailable or autoplay denied`, whatever went wrong: a redirect the host refused, a file over its byte cap, a slow or missing source, bytes that were not media, or autoplay. Checked against NAP-MEDIA (napplet/naps PR #10 @ 7806f438, Error Handling), the error is now the spec's category: `unsupported source`, `source blocked` or `autoplay denied`, with `source unavailable` for the rest. A typed cause follows in parentheses, such as `source blocked (blocked-by-policy: denied:redirect-unverifiable)` or `source unavailable (timeout)`. NAP-RESOURCE `blocked-by-policy`, `unsupported-scheme` and `quota-exceeded` count as blocked. New exports: `MediaPlaybackError`, which a custom backend throws to name a cause, `mediaCreateError` and `mediaResourceError`. An error that is not typed still reads only `source unavailable`, so a backend's own message never reaches the napplet. The parenthesised cause is a kehto choice, because NAP-MEDIA's result carries only the `error` string. A host that matched the old string must match the new categories.
