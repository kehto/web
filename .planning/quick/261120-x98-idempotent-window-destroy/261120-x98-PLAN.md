# Quick 261120-x98: one onWindowDestroyed per registration (kehto/web#498)

Spec: no NAP wire surface. `onWindowDestroyed` is a Kehto-internal service hook; no NIP-5D or
NAP message, field, or direction changes. NIP-5D port binding and Paja load provenance untouched.

## Findings (staging `99353c60`)
- With the permission runtime, a Paja Firewall retire notified services 3 times: admission
  `destroyWindow`, `sessionRegistry.unregister` -> `onRetire`, then #495's bridge revoke
  `destroyWindow` again. The first `register()` of a window also sent a spurious destroy.
- Without permissions, a repeated `destroyWindow` notified twice.

## Tasks
1. RED: `packages/runtime/src/window-destroy-once.test.ts` (every teardown order, re-registration,
   replacement, `sessionRegistry.clear`, permission revocation kept separate, never-registered
   windows unchanged, spent-set bound); Paja `browser-target-frame-retire.test.ts` asserts exactly
   one destroy and one `onPermissionRevoked` (fails on staging).
2. GREEN: `createWindowDestroyTracker` in `service-dispatch.ts` (live registrations + bounded
   spent set); `runtime.ts` routes `destroyWindow`, `onRegister`, `onRetire` through it.
3. Audit: upload, relay-pool, webrtc, CVM handler/admission tickets, llm, resource, dm, media,
   serial, config, Paja notify/device/webrtc-profile `destroyWindow`: all map-delete or
   idempotent-ticket based; none relied on a second call. Runtime `destroy()` sends no window
   destroys (unchanged).
4. Docs (runtime/shell/paja package docs, JSDoc) + `@kehto/runtime` patch changeset.
5. Follow-up: without the permission runtime a source stays live after a cleanup `destroyWindow`
   (documented legacy semantics, pinned by `firewall-registration.test.ts`). Blocking its dispatch
   would break that, so a registered source that dispatches again is re-armed and its next destroy
   notifies. With permissions, `permissions.close` already retires the source, so nothing changes.
