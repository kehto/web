# Fail relay.publishEncrypted closed when the signer can't encrypt (kehto/web#482)

Scope: `handleRelayPublishEncrypted` / `publishEncrypted` in
`packages/runtime/src/relay-handler.ts` fell back to `?? ''`. A signer with no
`nip44`/`nip04` therefore produced a signed, published, empty-content event and
`ok: true`.

## Contract

- NAP-RELAY napplet/naps#2 head `9f30b350` (re-resolved 2026-11-20, unchanged).
  Shell Behavior: "The shell MUST encrypt content and sign event templates from
  `relay.publishEncrypted`, forward the signed encrypted event to its relay
  pool, and respond with `relay.publishEncrypted.result` containing the signed
  event." Error Handling: a failed publish is `.result` with `ok: false` and
  `error`. The NAP has no error code list, so Kehto uses diagnostic strings.

## Decisions

- Check for the scheme's `encrypt` before planning or authorization, so a
  broken signer never triggers a consent prompt.
- After encryption, reject a non-string, empty or plaintext-equal result.
- Conformance fixture signer gains real NIP-44 v2 / NIP-04 (`nostr-tools`).
  The relay check is unchanged. #478 listed the success path as not proven
  only because the fixture couldn't encrypt.
- "NIP-44 by default, NIP-04 as fallback" (API Surface) is read as naming the
  alternative value, so an omitted scheme with a NIP-04-only signer fails closed
  instead of downgrading silently. This is a spec gap, with an upstream question
  in the PR.
- Relay services: the runtime always handles `relay.publishEncrypted` itself
  (`relay-handler.ts` `case 'publishEncrypted'`). It hands the service only a
  `relay.publish` carrying the signed event (`publishSignedRelayEvent`,
  `executeRelayOperation(windowId, { type: 'relay.publish', id, event: signed })`).
  So `relay-pool-service.ts`'s `publishEncrypted` branch (a fallback for
  alternate wirings, per its header) and `coordinated-relay.ts` (planning
  only) never see a plaintext template through the runtime. Nothing changes
  there.
