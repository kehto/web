# Audit remaining browser UUID assumptions (kehto/web#351)

## Live audit (origin/main `b29e2a70`)

The issue's file list was stale: `apps/playground` is retired, and main had grown new unguarded callers.

| Site | Before | Contract | Change |

| `paja/browser-nip46-client.ts` (5 request ids) | `crypto.randomUUID()` | secure | shell `randomUUID` |

## Decisions

- One policy, two homes. `@kehto/shell` now exports `randomUUID`; Paja already depends on the shell. `@kehto/services` keeps a private twin rather than a services -> shell edge, and `tests/unit/random-uuid-sync.test.ts` fails on drift. `@kehto/runtime` was rejected as a shared home because it takes crypto through `RuntimeAdapter` hooks and reads no globals.
- No new option on `createUploadService`; the existing `generateId` injection point is unchanged and its default is now secure.
- HTTP claims stay scoped. Regressions prove approval-scoped uploads and CVM registry verification still fail closed without `crypto.subtle`. The issue's mention of a digest in `cvm-nostr-transport.ts` no longer matches main; the CVM digests live in `cvm-schema-hash.ts` and `cvm-progress-controller.ts`.
- Protocol check: NAP-SHELL, NAP-INTENT, NAP-INC, NAP-IDENTITY at `napplet/naps@377bf939c6c906817084b43dd21d424de646dbc2` treat ids as opaque correlation strings. NAP-UPLOAD, NAP-CVM, NAP-MEDIA and NAP-RESOURCE have no merged document on master; the packaged `@napplet/nap@0.40.0` types declare the ids as plain strings. No wire, source-trust, or readiness change.
