# OpenAI Responses dialect for `createHttpLlmProvider` (kehto/web#414)

Scope: a fourth host-side provider dialect, `openai-responses`, next to `openai-chat`, `anthropic-messages` and `gemini` in `@kehto/services`, with streaming, tool calls and reasoning summaries, plus an opt-in endpoint profile for subscription-backed sign-in tokens. The napplet-facing wire does not change.

## Contracts and decisions

- NAP-LLM: napplet/naps PR #134, head re-resolved on 2026-11-20 and still `5e93bdfce0e84c0de728234cb7b3feed498f8635` (open, unmerged). Provider mapping is permitted; provider restrictions are `unsupported` before submission; missing markers are `provider-error`; thinking is display-only; `isError` without a native flag is a leading `Tool execution failed.` text part.
- Responses wire shapes: official SDK types `openai@7.62.0` (openai/openai-node `02e2995540d35d92d7f6e814ee40009cc9c8c83d`, `src/resources/responses/responses.ts` and `src/resources/shared.ts`), read as data. Not from memory.
- Sign-in limits: `developers.openai.com/siwc/token-sharing-open-source` and its `preview-limitations` and `models-and-inference` pages, fetched 2026-11-20. They confirm `store: false`, `stream: true`, no `max_output_tokens`/`temperature`/`previous_response_id`, no system-role items, and namespace-grouped function tools. `namespace` on `function_call` input items comes from the SDK type only.
- Stateless by design: full history in `input`, `store: false` always, no `previous_response_id`, no `include`.
- Assistant history is sent as `{type:"message", role:"assistant", content:"<text>"}` (`EasyInputMessage`), because the typed `output_text` form needs provider item ids the adapter does not keep.
- The terminal event's `output` array is authoritative; streamed items are the fallback when a server leaves it empty.
- Unverifiable points are refused, not guessed: a forced tool name under the sign-in profile, tool history without tools under that profile, and images in assistant history.
