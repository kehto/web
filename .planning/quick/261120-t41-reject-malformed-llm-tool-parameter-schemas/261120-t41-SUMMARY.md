# Reject malformed NAP-LLM tool parameter schemas (issue 401)

## Finding

The issue predates tool support. On main at `b29e2a70` its three literal cases already passed: `{ type: 'object', properties: 5 }`, `{ type: 'object', required: 'city' }` and `{ type: 'array' }` were `invalid-request`, and a schema using `properties`, `required`, `enum` and `$defs` was accepted. The check behind that was partial, though. It covered `type`, `required`, `enum` and the common subschema keywords, so 46 of the 66 meta-schema-invalid vectors in the new table reached the consent prompt on main (for example `minLength: '3'`, a boolean `exclusiveMinimum`, `required: ['a', 'a']`, `unevaluatedProperties: 5`, `$ref: 5`).

## Change

- `packages/services/src/llm-json-schema.ts`: one rule per keyword of the 2020-12 meta-schema (core, applicator, unevaluated, validation, meta-data, format-annotation, content, and the deprecated keywords it still describes). Unknown keywords pass.
- `packages/services/src/llm-validate.ts`: `toolParameters` calls it after the existing `isJsonValue` bound and the root `type: "object"` rule.
- Hand-written on purpose. Ajv compiles validators with `new Function`, which a CSP without `unsafe-eval` refuses, and its standalone output would add generated code and a build step for about 60 flat rules. Ajv is a devDependency used only as a test oracle.
- No regex is compiled or run, and no `$ref` is resolved.
