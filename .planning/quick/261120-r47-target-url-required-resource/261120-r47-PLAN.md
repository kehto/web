# Open target-url napplets that require resource (kehto/web#447)

Scope: `kehto paja --target-url` refused every development document listing `resource` under `napplet-requires`, with only `Paja Firewall launch admission incompatible: resource` inside the frame. Reproduced on main with the issue's page: `admitBrowserDocument` returns `incompatible` because Paja always passes the dev origin as a remote source.

## Contracts and decisions

- Authority: NAP-RESOURCE PR 80 head `ae5b9c64ab8a4d8909f288829a01e99d6bd713bc` (`naps/NAP-RESOURCE.md`, resource binding in `projections/web.md`), rechecked via GitHub; master `377bf939` has no NAP-RESOURCE. The binding requires blocking direct fetch, XHR, WebSocket, EventSource, beacon and external subresource loads before exposing `resource`, and forbids applying the direct-network exception to such a napplet.
- Today's live frame CSP grants the dev origin on script-src, style-src, img-src, font-src, worker-src, media-src and connect-src (plus the ws origin). That is direct network.
- Rejected: "assets only, connect-src closed". External subresource loads are named by the spec, and img/script loads to a loopback origin are egress the resource policy must block.
- Rejected: opt-in flag with a warning. The host would knowingly expose `resource` to a frame it cannot isolate, which the binding forbids.
- Chosen: when `resource` is required, load the fetched `index.html` as a network-isolated snapshot (no remote sources, no base URL), the same closed CSP as a local single-file target. Shell admission is untouched; verified and local-file paths are untouched.
- Also: say it up front. CLI startup notice, `/__kehto/target-network.json`, message-log entries for the snapshot and for an omitted optional `resource`, and an actionable error when host-granted origins still conflict.
