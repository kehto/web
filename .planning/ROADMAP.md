## Active Milestone: v1.30 Experimental IPC Shell Projection

**Goal:** Build an experimental Unix-domain-socket shell projection that
carries canonical NIP-5D envelopes between a host and a napplet process and
produces implementation evidence for a future `napplet/naps` IPC specification.

**Authority:** `napplet/naps` `origin/master` at
`c0f7dd14460622fc3a9870ea57a538474cf776fa`. No IPC projection exists at that
ref. NAP-SHELL and NAP-INC carrier-neutral invariants remain authoritative;
all IPC-specific framing, endpoint, and lifecycle choices are experimental
findings rather than normative protocol behavior.

**Hard constraints:**

- Create a separate Node/POSIX `@kehto/shell-ipc` package; do not change the browser `@kehto/shell` projection.
- Use dedicated pathname Unix-domain stream sockets and canonical NIP-5D envelopes; do not introduce Tauri, Electron, TCP, WebSocket, Windows named pipes, or shared-listener multiplexing.
- Identity and environment are registered by the host before listen and are never accepted from peer messages.
- Provide no `window.napplet.*` injection and no napplet-side Kehto client helper; the reference peer uses raw `node:net`.
- Reuse `@kehto/runtime` dispatch, ACL, capability, and session semantics through its public transport seam.

## Phase Details

### Phase 107: IPC Transport Foundation

**Goal:** Host integrators can create a bounded, private, identity-bound Unix-domain socket endpoint that safely transports canonical NIP-5D envelopes.
**Depends on:** Nothing
**Requirements:** IPC-01, IPC-02, IPC-03, IPC-04, BIND-01
**Success Criteria** (what must be TRUE):

1. A host registers immutable identity and environment metadata before creating one dedicated pathname socket in a short private directory.
2. Raw stream input produces unchanged canonical envelopes across partial and coalesced chunks using the documented RFC 7464 framing contract.
3. Malformed, truncated, invalid-UTF-8, oversized, and over-buffered input fails closed before runtime dispatch.
4. Outbound messages remain ordered and bounded while socket backpressure is respected.
5. Stale-path recovery and cleanup remove only resources owned by the matching endpoint registration.

### Phase 108: Runtime Shell Composition

**Goal:** Connected napplet processes receive the same authenticated NAP-SHELL and runtime guarantees as the web projection through IPC-specific lifecycle binding.
**Depends on:** Phase 107
**Requirements:** BIND-02, BIND-03, BIND-04, PROOF-01, PROOF-04
**Success Criteria** (what must be TRUE):

1. `@kehto/shell-ipc` composes the public `@kehto/runtime` seam without altering canonical envelopes, runtime dispatch, or browser `@kehto/shell` behavior.
2. Each registration has at most one active peer, and generation checks prevent stale connection events from destroying replacement state.
3. One bare `shell.ready` establishes the source-bound session and produces exactly one `shell.init`; duplicate ready is idempotent.
4. Capability traffic before readiness is rejected or ignored consistently, while post-ready traffic remains subject to existing ACL and capability eligibility.
5. Graceful close, abrupt disconnect, unregister, and host shutdown clean up only the matching session, connection, listener, path, and owned directory.

**Plans:** TBD

### Phase 109: Runnable Proof and Drafting Evidence

**Goal:** Maintainers can run and evaluate the experimental projection as a publishable package and use its recorded findings to draft an upstream IPC contract.
**Depends on:** Phase 108
**Requirements:** PROOF-02, PROOF-03, PROOF-05, SPEC-01, SPEC-02, SPEC-03, SPEC-04
**Success Criteria** (what must be TRUE):

1. A reference host and raw `node:net` napplet process complete a correlated request/result round trip with no injected interface or Kehto client helper.
2. The same process receives a runtime-originated push message, and both graceful and abrupt process termination leave no live route or owned socket resource.
3. `@kehto/shell-ipc` builds as a publishable ESM package with complete API/README/package documentation and a conspicuous Node/POSIX experimental stability warning.
4. A web/IPC parity matrix and drafting findings document record the checked upstream ref, shared and carrier-specific responsibilities, security assumptions, bounded choices, and unresolved questions.
5. Focused transport and process tests plus the Changeset, build, type-check, unit, relevant end-to-end, docs, and AI-slop gates all pass.
